# 波束来源关联与协作 AssociationRecord

状态：字段契约 0.1.0 已有 [Schema](../assets/schemas/AssociationRecord.schema.json)、[待确认模板](../assets/templates/AssociationRecord.draft.json) 和只读结构检查。三个层次已实现显式入口，见 [协作执行 v1](association-runtime-v1.md) 与 [框架范围](framework-v01.md)。格式本身不触发查询、计算或调度。

## 第一层 双向索引

索引连接上游波束结果、明确波束信号、检测任务、候选和所选产物。它是 provenance/result index，不是候选—轨迹数据关联、物理声源关联或目标归属。不得产生 `track_id`、`source_id`、`target_id`、`harmonic_family_id` 或 `same_target` 结论。单阵元不伪造波束节点。关联记录包含：

| 内容 | 约束 |
|---|---|
| record_id / schema_version | 记录身份和契约版本 |
| entities | 来源包/结果、信号、task、run、candidate、artifact 等显式身份 |
| relations | 实际来源/派生/比较关系及其依据，不能仅凭同频就建立 same_target |
| scope_mapping | 各对象时间、样本、频率和方向对应；未知/不适用与映射依据分开 |
| evidence_refs | 可核对证据定位、摘要、是否随包及当前可用性 |
| persistence | 会话临时或已保存；反向查询仅在已登记且获准访问的范围内有效 |

主波束来源以结果摘要 + 波束算法 + beam_id 限定；输入以交接包摘要 + signal_id 限定；候选以 run_id + task_id + candidate_id 限定。保存列与扫描列分别使用，不拿角度数字或第一列替代身份。方向应附坐标系、零向和正向定义。

同一关系提供正反两个查询方向，无需向上游 result.json 回写字段。新索引另存；源只读且历史状态保持原样。原始路径变化但内容核对一致可重新定位；没有核对依据不得替换源。

来源未登记、未保存、只有引用或已不可读时明确报告；不自动搜索整台电脑的其他同名文件补齐。只有谱/图而缺少某束时域时，该束检测受阻，但已有空间结果仍可按其覆盖被查看，不冒充已检测该束。

## 第二层 按需联合查看与比较

比较请求明确左右/多方结果、要看的量、选定时间/频率/方向范围、对齐与解释规则，以及展示/保存选择。先审查已有证据，再判断是否需要新增计算。

可以按用户请求：由候选定位来源谱图；比较同向 CBF/MVDR 的检测表现；比较指定多个方向；结合已保存频率—角度或 BTR 等结果查看背景。不能默认遍历全网格、重做所有方向时域或重复检测。

可比性记录应覆盖实际数据范围、有效覆盖、频带、谱/检测设置、单位与参考、频率/时间坐标和已接受模型限制。同源记录不等于独立证据。统计量语义不同则分别展示并说明，不能按通用分数排名。

- “来源追溯”可以只有准确引用；“对应位置查看”需要坐标映射；“数值比较”还需要单位/定义/覆盖可比。三者不能互相冒充。
- 平均频率—角度结果不能证明某个瞬间的空间表现；频带汇总 BTR 不能冒充某条单频线谱的时间—角度证据。需要相应细分结果时另行提出计算。
- 不静默取最近频点/角度、插值、重采样、拼接时间或更改参考尺度。对齐规则若影响数值结论必须明确说明和确认。
- 缺时域不从功率谱反推波形；缺实际数值时不从图片宣称精确检测指标。
- 多个方向或算法同时有相近频率不自动合并为同一目标，也不自动要求两算法同时检出才保留候选。

比较完成只说明本次实际查看/计算的关系，不倒改各自原检测结果、门限或先前确认。

## 第三层 经确认进一步计算

FollowUpRequest 作为 followups 数组中的后续动作对象，不是执行许可。字段包括：

| 字段 | 说明 |
|---|---|
| parent_refs | 触发问题的运行/候选/产物及摘要 |
| question / reason | 用户希望解决的问题与提出追加的理由 |
| responsible_module | 语义上区分线谱检测、线谱评价、波束计算或已有产物展示/导出；实际序列化仍遵守当前 Schema，不自行增加枚举 |
| requested_action / scope | 明确要补算或交付什么，哪些信号/方向/时间/频带，不默认全扩展 |
| dependencies | 已有可复用证据、缺失输入、额外计算/中间量需求 |
| parameters / unresolved_items | 实际新增参数及待询问项；上游信息只在核对适用后继承 |
| resource_and_output_plan | 追加资源、展示和保存范围 |
| approval / status | 提议、待确认、受阻、确认、运行及结果状态，彼此分开 |
| result_refs | 实际完成后的新结果及与原结果关系；未运行保持未生成 |

先提出问题和方案，经用户选择与相关参数确认后，才由责任模块按其自身契约执行。波束补算使用波束模块，不在检测模块复制实现或绕过其方向/时域保留确认。跨模块调度要分别核对兼容性、来源、确认和状态。

查看候选、点击图、接受一项建议或另存结果不授权其他动作。一次补算不扩展为自动搜索、自动调参、选目标或持续反馈循环；提议状态不主动启动任务。

已有数据可用且参数/覆盖一致时可以提议复用；不满足条件时说明需重算，不能悄悄替换。新结果分配新运行身份和独立交付位置，保留父结果，不覆盖或删除已完成记录。

## 验收要求

后续验证正反查一致、不同包/算法同名ID隔离、保存列不混扫描列、未知方向不能定位、缺失文件不替代、仅看图不触发计算、比较差异充分记录、两算法结果不作独立真值、补算必须重新核对确认、新旧结果关联但互不覆盖。测试通过也不证明真实目标身份或物理方位正确。


## 0.1.0 序列化说明

entities 中单列 beam 身份，限定为 result_sha256 + beamformer_algorithm + beam_id；signal、candidate 等也有各自限定身份。relations 仅引用本记录声明过的 entity_id；反向查询已实现于明确提供的记录集合，非全局数据库。comparisons 和 followups 字段本身不自动执行，需显式入口与相应门禁。

填写步骤、draft / specified 的区别以及 CLI 用法统一见 [字段结构与待确认模板](schema-validation.md)。结构有效不证明事实、确认或执行状态真实。

## 独立评价后的协作边界

结果展示、身份映射和候选定位仍在公共协作设计内；真值匹配、指标计算、效果比较与验收规则由 [线谱评价 Skill](../../underwater-line-spectrum-evaluation/SKILL.md) 维护。已设计的三个协作层次不因此取消，也不变成自动执行。

评价记录是外部只读引用的消费者，不向旧结果补写结论或替换候选。其交接与未来对象语义见 [评价交接设计](../../underwater-line-spectrum-evaluation/references/evaluation-handoff.md)。当前 AssociationRecord 0.1.0 不保证支持独立评价对象或调度；需要时另行版本化扩展，不能用新名字冒充已经可运行的实体/执行器。
