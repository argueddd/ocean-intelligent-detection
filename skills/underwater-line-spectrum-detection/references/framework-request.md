# 检测请求与参数确认 DetectionRequest

状态：字段契约 0.1.0 已有 [Schema](../assets/schemas/DetectionRequest.schema.json)、[待确认模板](../assets/templates/DetectionRequest.draft.json) 和只读结构检查；新增 preflight 0.1.1 可做跨文档预检、问题汇总、方案绑定及独立用户表述记录；另有 [runtime v1 完整门禁与确认执行器](runtime-v1.md)，但仍不认证真实用户身份；旧预检边界见 [预检与确认状态](preflight.md)。参见 [框架范围](framework-v01.md)；不要把下列字段传给既有交接脚本。

## 请求对象

| 字段 | 内容与约束 |
|---|---|
| schema_version / request_id | 契约版本与本次请求标识 |
| tasks | 显式任务列表；每项有 task_id、明确 SignalInput 引用、detector_id 和 detector_version，不隐式构造信号×算法的全部组合 |
| scope | 每项任务的分析样本区间、搜索频率范围及时间/频率语义；全范围也需明确选择，不由空值推断 |
| resolved_parameters | 按算法说明整理的实际参数与处理步骤；没有选择算法时可以保留草案，但不可执行 |
| parameter_evidence | 参数值的上游出处、用户选择、建议待定或假设状态；不是所有事实都需要用户重新输入 |
| unknown_decisions | 未知项、影响、用户明确决定、适用动作及限制；不把接受未知改写为事实已知 |
| products | 分开的 compute、view、save 选择及必要依赖；缺失不是全部，明确空列表才表示不选择 |
| resources | 已确认输出位置/持久策略及与本次实现对应的资源预算，不复用其他试验的额度 |
| approval | 确认状态、绑定方案的摘要、用户确认依据；系统不能为自己生成用户同意 |
| parent_request / parent_result | 追加动作时的来源引用及其范围，不代替本次确认 |

每项 task 对应一条输入与一个检测实现，第一版独立运行。比较属于关联层的显式请求，不在 tasks 中暗中选取其他束；批量失败处理策略也要明确，不自动缩减批次。

## 参数与问题状态

| 情况 | 处理 |
|---|---|
| 有可靠来源的事实 | 继承值与证据，核对冲突，不重复索要 |
| 用户尚未选择 | 汇总有意义的选项，待决定 |
| 必需条件缺失或冲突 | 阻断受影响计算，不猜测或静默修复 |
| 可保留未知且不违反算法条件 | 说明影响并取得处理决定，保留 unknown 与限制 |
| 不适用 | 标为 not_applicable，不填0或默认值 |

待定 null/未填写值不是有物理含义的值；不能把空搜索范围当全频带。问题记录至少指出字段、缺口/冲突、受影响动作及需要的决定。能继续的只读检查不必一起停下，但不能在提问间隙执行被阻断的计算。

波束来源中的采样率、算法/方向、处理历史按输入契约继承；上游绘图窗参数不是检测参数。采样率/形状等计算必需事实缺失不能用“接受未知”绕过。

对于并非必需的方向、单位或背景信息，是否影响某项算法或比较需检查实际依赖，不把所有未知一律升级成无关问题。

## 确认对象与变更

确认绑定来源清单/消费文件身份、信号选择、算法版本/实现身份、分析范围、实际参数、影响结果的步骤、未知项决定、计算产物及资源边界。摘要只能证明配置一致性，不能替代真实用户确认。

发生以下变化时，对受影响动作重新确认：输入/版本、样本或频带、方法/处理参数、未知项处理、额外数值计算及显著资源变化。不得沿用此前测试许可，包括某个临时列序、0°方向或过去的 STFT 参数。

仅查看已有结果不重写旧计算授权。新增保存/导出仍须在用户明确请求内；更改显示若只渲染已有数值，不假称重新检测。若显示或比较需要新的谱、插值、重采样或计算统计，先声明为追加计算并确认。

“设计框架”“生成摘要”“检查请求”“接收完成”均不是检测授权；旧 handoff 的 can_detect=false 不改成 true，新检测请求另行记录自身状态。

## 执行顺序

1. 只读审查明确指定的输入及可用算法说明；仅做必要结构、来源和内容完整性核对，不计算信号特征来挑参数。
2. 汇总缺口、冲突、算法不支持项和输出依赖；未选算法只给待定方案，不自动选择。
3. 展示可执行范围、实际参数、未知处理、计算/显示/保存及预算，取得真实确认。
4. 运行前复核配置与源内容一致。获准执行不保证数值运行一定成功。
5. 运行后核对实际覆盖、来源未变、结果格式和请求产物，按结果规范发布状态。
6. 如需进一步计算，另建关联请求，不形成自动反馈循环。

runtime v1 实现上述流程，preflight 本身仍只做声明/文件核对与预检表述记录。specified、approval 字段或旧 recorded_current 均不能代替新 runtime 的 execution receipt。真实用户表述必须在对话中取得，工具只检查记录绑定，不认证身份。

## 失败与局部阻断

每项任务分别记录 not_run/blocked/running/completed/failed 状态及原因；整个批次只有所有请求任务和承诺交付均完成才可报全部完成。批次可能部分完成，但失败任务不得伪造空候选结果。

数值异常、超预算或来源变化需停止受影响计算，不自动换算法、降精度、补数据、缩短时段、减信号数或覆盖输出。是否继续独立任务按明确批次策略执行。部分文件不是完成结果；已完成的旧结果不删除。

## 门禁测试

必须覆盖未选择算法、缺条件必填参数、参数冲突、未知字段、输入摘要变化、版本变化后旧确认、不同任务混用确认、未知掩码被冒填、库默认值偷跑、输出依赖暗中补算、批次失败状态和仅查看结果不触发检测。其中请求/输入/算法身份匹配、条件必填、默认值不填充、文件变化、旧确认失效、输出依赖和只读行为已增加隔离测试；运行/科学参数/资源/输出/协作的合成回归另见 [运行入口](runtime-v1.md)，不等于实测效果验收。详见 [预检测试边界](preflight.md)；原单文档检查边界保持独立。


## 0.1.0 序列化说明

scope、resolved_parameters、processing_steps、parameter_evidence、products 位于 payload.tasks[]；resources、approval 和 batch_failure_policy 位于 payload。每项 task 只指一条信号和一个检测实现，不自动构造批量组合。

填写步骤、draft / specified 的区别以及 CLI 用法统一见 [字段结构与待确认模板](schema-validation.md)。结构有效不证明事实、确认或执行状态真实。
