## 1. 系统定位与总览

知识库（KnowledgeCore）是 DeepSeek Harness（dsh）之上的**公司制度知识底座**，并带有一套**知识飞轮（Knowledge Flywheel）**机制，使知识库具备自我感知、自我体检、受控进化的能力：

- 数据来源：公司制度文档（1800+ 篇）、会话沉淀的结论、人工新建的概念与关系；
- 使用方式：日常对话中检索；知识库工作台（8 个页签）可视化操作；
- 核心保证：任何一次知识变更都必须**经过考试、全程记账**，且支持自动回滚。

整体分三层：

```text
┌─ 用户层：dsh 对话 + 知识库工作台（浏览器 UI）──────────────┐
│  会话工具：lightrag_query / kb_ingest / kb_update /        │
│           kb_propose / kb_analyze / kb_report / kb_status  │
│  审批卡：破坏性操作需要人工批准                               │
└──────────────┬────────────────────────────────────────────┘
               │ 进程内调用 + HTTP 路由（/kb/*）
┌──────────────▼────────────────────────────────────────────┐
│ dsh-knowledge 插件（Node，profile bundle）                 │
│  engine-port.js —— LightRAG REST 适配器（怪癖集中地）+ 假引擎 │
│  service.js   —— 单一写入口：origin 策略链 + 幂等 + 审计     │
│  intent.js   —— 意图账本：WAL + 状态机 + 串行执行器        │
│  reconciler.js —— 收敛器：引擎↔注册表持续对账              │
│  registry.js —— 文档注册表 + 审计流水（append-only）        │
│  curator.js  —— 查询日志/提案账本/评测集（golden）+ 回放层  │
│  gate.js     —— 提案应用/回滚 + 双条件门控 + 指纹锚定基线   │
│  analyze.js  —— 五类健康分析 + 运营周报                     │
└──────────────┬────────────────────────────────────────────┘
               │ HTTP（127.0.0.1:9623）
┌──────────────▼────────────────────────────────────────────┐
│ LightRAG 引擎 v1.5.6（容器 hkuds/lightrag，上游未 fork）    │
│ 解析(文本入库) → 抽取实体/关系 → 图+向量双索引 → 多模式检索  │
│ 存储：JsonKV + NetworkX GraphML + NanoVectorDB（文件型）    │
```

## 2. 核心设计原则

1. **单写者**：知识库的所有变更只通过 LightRAG HTTP API 提交（经 dsh-knowledge 插件）。插件侧不做任何绕过 API 的写盘操作，引擎的并发保护（keyed lock / pipeline busy 检查）全程有效。
2. **评测先于提交**：additive 提案必须通过"自证题 + 回归考试"双条件才生效；考试不过自动回滚。
3. **人工兜底**：破坏性操作（删除/合并/文本入库）不依赖自动考试，必须人工审批。
4. **全程记账**：查询有流水（query_log），变更有序时账本（proposals + audit），任何状态可回溯、可解释。
5. **不在引擎上打补丁**：LightRAG 保持上游版本（不 fork），信号采集与治理逻辑全部放在插件层，升级引擎不受牵连。

## 3. 数据模型与落盘位置

插件数据目录 `storages/dsh-knowledge/` 下的文件全部为 append-only 或可重建的管理数据：

| 文件 | 内容 | 说明 |
|---|---|---|
| `registry.json` | 文档注册表 | 版本链、主题、状态机（pending→processing→active/failed/retired/outdated） |
| `audit.jsonl` | 审计流水 | 全部写操作一行一条，不可删改 |
| `query_log.jsonl` | 查询流水 | 每次检索：时间/会话/问题/模式/命中引用/耗时/入口 |
| `proposals.jsonl` | 提案账本 | 状态迁移=追加新行（同 id 末行生效），不可变可回溯 |
| `curation_runs/commit_log.jsonl` | 提交流水 | 每次生效的提案与门控结果 |
| `reports/` | 体检报告与周报 | `analysis-*.md/json`、`weekly-*.md/json`、`baseline-*.md/json` |

引擎活库 `rag-storage-0.6B/` 的三类存储（仅读，不直接写）：

| 文件 | 角色 |
|---|---|
| `graph_chunk_entity_relation.graphml` | 图谱本体（217MB，约 10.9 万实体节点；节点的 d0/d1/d2 属性=实体 id/类型/描述） |
| `kv_store_*.json` | 键值索引（其中 `kv_store_full_entities.json` 是"文档→实体名"删除索引，键为 doc-<hash>，**不是实体档案**） |
| `vdb_*.json` | 向量库（951MB，NanoVectorDB 格式，供语义检索） |

## 4. 知识飞轮机制

飞轮回答一个问题：**知识库如何"越用越聪明"且"不会变坏"。** 五个环节首尾相接：

```text
① 信号采集（自动）     每次检索自动记录 query_log
        ↓
② 健康分析（体检）     kb_analyze 五类分析：源冲突 / 失败文档 / 重复实体 / 检索缺口 / 图谱提示
        ↓
③ 提案（原子交易）     一条提案一个操作，必须带证据链 + 理由 + 自证题
        ↓
④ 双条件门控（考试）   自证题：改前答不上、改后答得上（否则判冗余/无效并回滚）
                        回归题：29 道 golden 考题重跑，分数不许掉（否则回滚）
        ↓
⑤ 审批分级 + 记账       additive（补描述/建概念/补关系）考试通过自动生效；
                        破坏性（删除/合并/文本入库）弹审批卡，人工批准后生效；
                        全部过程落三本账
```

### 4.1 检索缺口三分类（②→③ 的桥梁）

对 query_log 中零命中的查询去重后重新探测，自动分诊：

| 分类 | 含义 | 处置 |
|---|---|---|
| `a-missing`（库里没有） | 重新探测仍无任何结果 | 知识采购：调研后以 text_ingest 验证入库 |
| `b-retrieval-jitter`（偶尔波动） | 同参数重试即命中 | 检索波动，观察趋势，暂不处置 |
| `b-missing-text`（内容不全） | 实体能命中、条文检不出 | 最有价值：描述增强（entity_edit）或补条文（text_ingest）提案 |

### 4.2 门控判定口径（工程实测修正）

- **判定指标只取两项**：文档命中率（"找得到"）与引用覆盖率（"读得全"），容差 2%；
- **实体命中率（"认得全"）只记录趋势、不入判定**：实测引擎关键词抽取存在 3%~7% 的单轮批次噪声，硬性门控会误杀正常提案（首个真实提案即遭遇此问题，已修正）；
- 自证题判分：期望文档全部命中 + 期望条文全部命中 + 期望概念至少命中一个。

### 4.3 回滚与向量一致性

- additive 操作支持自动回滚：entity_edit 回滚=前值重放（前值从**活库 GraphML 节点 d2 描述**流式读取，约 0.3 秒）；entity_create/relation_create 回滚=删除刚创建的对象；
- 前值捕获失败时**自动降级为人工审批路径**（绝不"应用了却回不了"）；
- 向量数据无需插件操心：引擎的编辑/创建/合并 API 内部完成**重新嵌入**（`aedit_entity`/`aedit_relation` 等会删除旧向量并 upsert 新向量），且带 `VectorStorageConsistencyError` fail-loud 保护——图改成功但向量写失败会直接报错，绝不静默不一致。

## 5. 关键工程决策与理由（决策记录）

| 决策 | 理由 |
|---|---|
| 不 fork LightRAG | 引擎跑上游镜像，升级零负担；图谱编辑/合并/源冲突路由上游已自带 |
| 查询信号在插件层采集 | 所有查询必经插件（工具 + /kb/* 路由），能带上会话 id 等更富上下文，且不侵入引擎 |
| 门控用"线上前后对比 + 自动回滚"，不建快照沙盒 | 活库 4GB+，快照+双实例运维成本高；additive 天然可逆，考试用 /query/data（不生成回答）零费用零方差 |
| golden base 用 24h 内最近基线缓存 | 单提案门控只需跑一遍 29 题（约 1 分钟） |
| 周期编排：运营会话 + 周提醒 + goal 延续 | harness 的 schedule 是会话内提醒（非 cron，需在预设挂载 `@deepseek-ai/dsh-schedule`），审批只能在对话回合内发起——"提醒把人拉进会话"是原生正确姿势；未挂载时用 goal 延续 + 每周手动一句话触发 |
| 重复实体合并 v1 用别名法 | 引擎级 merge 涉及锚点重写，有破坏 purge 契约风险；先以 same_as 关系 + 描述并入主实体，拿 80% 收益 |
| 文本入库走人工审批 | 文本抽取是异步管线，删除重建成本高（分钟级全图重建），不适合自动考试路径 |

## 6. 部署与配置

| 配置项 | 说明 |
|---|---|
| `KB_RAG_STORAGE` | 引擎活库的**宿主路径**（上文 §1 表格），供重复实体扫描与 entity_edit 前值捕获；不配置时这两项能力自动降级 |
| `KB_LIGHTRAG_INPUTS_DIR` | LightRAG inputs 的**宿主路径**（含 `__parsed__`），供图文关联（证据片段携带原文档图片 + `/kb/image` 图片服务，机制见[重构后功能说明](重构后功能说明.md)）；不配置时自动降级 |
| `LIGHTRAG_BASE_URL` | 引擎地址，默认 `http://127.0.0.1:9623` |
| `KB_DATA_DIR` | 插件数据目录，默认 `${DSH_HOME}/storages/dsh-knowledge` |
| `registry.settings.auto_commit_ops` | 免审批自动生效的操作白名单，默认 `['entity_edit','entity_create','relation_create']` |

发布方式：修改 `dsh-knowledge` 包内代码后，**重启宿主进程 + 页面刷新**生效（技能与 golden.yaml 由文件监视器即时生效）。

## 7. 已知边界与后续演进（P3 候选）

- 破坏性操作目前不做自动化评测（人工审批即门控）；
- 用户踩赞（feedback）与历史会话日志的"双源信号"合并尚未接入（接口限制，见 DESIGN §11.6）；
- 无快照沙盒评测（批量参数调整等场景再评估引入）；
- 引擎级实体完整合并（含锚点重写）需先补 purge 契约回归测试；
- 多知识库（分部门分库）预留了 `kb` 参数，未启用。
