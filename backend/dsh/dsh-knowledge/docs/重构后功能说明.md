# 反馈驱动的知识库诊断与修复助手

当前版本围绕一条闭环工作：用户查询、提交负反馈、运行诊断、审批修复提案、查看执行状态并复核原问题。产品定位为“反馈驱动的知识库诊断与修复助手”——系统能够从真实反馈中发现问题、解释原因、提出可执行修复建议，并由用户审批后修改知识库；不承诺“自动学习、自动变准”。

工作台分四个一级视图：**总览**（知识库运营指标）、**文档与图谱管理**（文档列表 / 添加文档 / 图谱管理）、**反馈与诊断**（诊断总览 / 反馈与诊断 / 修复提案 / 执行记录）、**健康体检**（知识库健康体检）。

## 知识库运营总览（总览页）

知识库作为资产的运营数据（与诊断域指标互补）：

- **知识资产**：文档总数、近 7 天新增、处理中、失败数，以及主题分布（Top 8）。
- **检索信号**：近 7 天查询总量、零命中查询与零命中率、高频查询 Top 5。
- **知识变更**：近 7 天变更总数与分类（入库 / 文档变更 / 图谱编辑）及来源（工作台 / 智能体 / 系统）。
- **知识健康**：失败文档数、上次体检时间、健康体检入口。

## 诊断运营指标（反馈与诊断 → 诊断总览）

从反馈与诊断账本自动汇总的 10 项指标 + 问题层级分布，衡量“越用越准”：负反馈重复率、相似问题聚类准确率、提案批准率、提案拒绝率、提案执行成功率、用户确认解决率、用户确认仍有问题率、问题重新出现率、模型输出需人工补充比例、问题层级分布（knowledge / graph / retrieval / answer_generation / user_expectation 计数）。指标分母为 0 时显示 –，不臆造 0%。

## 知识库健康体检（一级视图）

一键触发 kb_analyze 同款的四类健康分析（全程只读）：源冲突（同一来源多版本并存）、失败文档与抽取状态、重复实体候选（名称变体聚类，需配置 KB_RAG_STORAGE）、检索缺口三分类（零命中查询重探分诊：知识缺失 / 检索波动 / 内容不全）。零命中重探异步执行（约 10-30 秒），完成后报告落盘 reports/ 并自动刷新；失败文档可跳转「文档管理」重试，重复实体可跳转「实体检索」合并。模型在对话中同样可用 kb_analyze 工具触发。

## 诊断总览（反馈与诊断页首子页）

诊断闭环的状态入口：待处理反馈 / 待审批提案 / 执行中任务 / 知识文档四张卡片、下一步建议与最近修复记录，以及诊断运营指标（10 项）与问题层级分布；引擎健康详情统一在「健康体检」一级视图查看。

反馈记录查询、回答、引用和会话消息标识。负反馈需要选择问题类型或填写说明，问题类型包括内容缺失、引用不准确、引用不完整、实体不准确、关系不准确、内容过期和回答方式。

## 智能诊断（模型语义分析）

在 AI 助手对话中说“诊断知识库负反馈”，智能体按三步编排：

1. `kb_feedback_inbox`：读取待处理负反馈摘要（反馈 id、关联查询、问题类型、备注预览），不加载正文，节约上下文。
2. `kb_feedback_context`：按 feedback_id / query_id 读取完整上下文——反馈提交时留存的问题、回答与引用，当时的 LightRAG 检索证据（实体 / 关系 / chunks / 引用文件）、涉及的注册文档、相似反馈。反馈未关联查询记录时自动用留存的问题原文实时重查一次补齐证据；需要最新状态时设 refresh_retrieval=true。
3. `kb_diagnosis_submit`：提交结构化诊断案例（问题层、根因、证据、建议动作、变更参数、置信度、待补信息、推荐标记），一次最多 10 个案例。

反馈提交链路：聊天中的「反馈此回答」从会话快照留存用户问题、回答正文和 lightrag_query 工具卡上的引用文件与查询 id；查询 id 把反馈关联到 query_log 中的检索快照，无关联时诊断工具退回实时重查。

证据式问答：`lightrag_query_data` 是问答首选工具——返回一次查询的原始检索数据（chunks、实体、关系、引用文件，不生成答案），智能体基于原文证据自行组织答案并注明引用来源，检索快照随查询记录内联落盘。`lightrag_query`（LightRAG 引擎直接生成答案）保留为可选路径，适用于需要原生生成风格或作为证据不足时的对照。

服务端在落库前做确定性校验：feedback_id / query_id 真实存在、chunk 与文件证据属于该查询的检索结果、action 与 payload 匹配（add_text 要 title+text；edit_entity 要 entity_name+updates；edit_relation 要 src+tgt+updates）、edit 目标实体在图谱中真实存在、cause_layer 与 confidence 落在枚举范围。校验失败的案例不丢弃，降级为“需人工核对”并保留错误清单。

大模型负责理解和判断，代码负责证据校验、权限控制和实际修改；模型只能生成提案，不能直接修改正式知识库。

## 图文关联（原文档图片随证据展示）

配置 `KB_LIGHTRAG_INPUTS_DIR`（LightRAG inputs 宿主路径，含 `__parsed__`）后，`lightrag_query_data` 的证据片段可携带原文档图片，图片 URL 由 `/kb/image` 端点按需返回图片字节（解析强制约束在 `__parsed__` 目录内，防路径穿越）。未配置时检索行为与原先完全一致。

两条注入通道（互不干扰，与 qa-assistant 参考实现同机制）：

- **占位符替换（普通 chunk）**：content 里的 `<drawing path="..."/>` 标注“图在哪”，可定位到图片文件时原地替换为 `![图片说明](http://…/kb/image?…)`；不可定位时移除（对模型是噪音）。
- **mm 反查追加（图片语义块）**：chunk id 形如 `doc-<hash>-mm-drawing-NNN` 的块是 VLM 写的图片描述（能被检索命中但自身不带图），按末尾序号反查该文档 `.drawings.json` 拿到原图路径后在描述末尾追加图片链接。反查做三级校验（hash 前缀 → 图片名相等 → 相似度 ≥0.75，difflib 口径），都不过则宁可不给图、不给错图。

带不带图由模型决定：工具规则要求“图片与回答内容直接相关时，把该图片的 Markdown 原样复制到回答的合适位置，不要修改 URL，也不要凭空编造”。前端聊天区渲染绝对 HTTP(S) 图片 URL，模型复制的图片语法直接显示。

已知边界：

- `.parsed` 目录被删的旧文档：两条通道都带不出图（无从定位），占位符移除、mm 块不追加；
- EMF/WMF（Word 矢量图，浏览器不可渲染）：`/kb/image` 经 libreoffice headless 转 PNG 后返回（缓存 key=路径+mtime，首次约 1 秒，命中 0 毫秒）；libreoffice 不可用时降级返回原文件，前端回退为图片说明文字；
- 引擎重新生成的答案路径（`lightrag_query`、`/kb/query`）不做注入——引擎自建上下文与提示词，插件无法在生成前介入，证据式问答是图片展示的唯一路径。

## 问题分层与动作

每条诊断案例必须归入一个问题层，决定修复方向：

| 问题层 | 典型问题 | 修复方向 |
|---|---|---|
| knowledge 知识内容 | 内容缺失、内容过期、文档冲突 | 补充或替换知识 |
| graph 图谱结构 | 实体错误、关系错误、实体重复 | 修改实体或关系 |
| retrieval 检索过程 | 相关内容存在但未命中、切分不合理 | 调整 chunk、检索参数或索引 |
| answer_generation 回答生成 | 答案误读、引用错配 | 修改回答提示词或生成策略 |
| user_expectation 用户预期 | 问题超出知识库范围或表述不完整 | 人工澄清 |

可执行动作（add_text / edit_entity / edit_relation / replace_document / review_document）在 payload 完整且校验通过后进入“待你确认”。建议类动作（reindex_document / adjust_chunking / adjust_retrieval / prompt_fix / manual_review）不可直接执行，固定为“需人工核对”，且必须把处置建议分条写进 payload.advice——每条是运维者或提问用户可执行的操作指令，以六类前缀开头：【改文档】（文件名、位置、具体内容）、【改图谱】（实体/关系的名称、操作类型——新建/编辑描述/删除/合并、具体内容，在「文档管理 → 实体检索」页执行）、【核对】（用什么问题重新提问、预期看到什么）、【配置】（哪个页面改什么参数）、【不改】（无需修改及原因）、【改提问】（当前提问哪里不清晰、下次怎么问，附改进示例）。缺 advice、空 advice 或无前缀的策略性描述均降级为“需人工核对”，避免把检索或回答层的问题错误地当成知识缺失来修。图谱操作分工：编辑已有实体/关系的描述走 edit_entity / edit_relation 可执行提案；新建、删除、合并属破坏性操作，不自动执行，由【改图谱】指令引导人工操作。

诊断汇报规范：面向用户的结论用全中文，不出现内部 id（feedback_id/query_id 只在提交案例时使用，叙述用问题原文指代）；每条案例按「问题（用户感知的现象）→ 根因（证据支撑的判断，注明出处文件）→ 怎么处理（要不要动知识库、动哪个文档、提问怎么改，还是无需处理）」三段分条说清。工作台提案卡同步展示根因与处置建议清单。

## 检索快照

每次经知识库入口的查询（网页检索、流式检索、模型工具检索）完成后异步补挂一份裁剪的检索快照（5 个 chunks × 3000 字符、20 个实体、30 个关系），不增加查询延迟；诊断时优先用快照还原“当时检索到了什么”，必要时实时重查对比当前状态。

## 审批与执行

界面按“推荐处理”（最多 3 张，高频且证据充分）与“全部候选”分组展示提案。用户批准后，系统仅执行具备完整参数且已支持的动作：补充文本、编辑实体、编辑关系。文档替换、来源核查保留为人工处理状态。

## 复核与用户判定

执行完成后可“复核原问题”：系统按 query_id 严格定位原始查询（不再按文本匹配），重放检索并对比前后引用与回答变化。用户还需明确选择判定：已解决 / 部分解决 / 仍有问题 / 无法判断，可附说明；判定记录随提案保存，是后续优化诊断质量的数据来源。

## 快速诊断（规则 fallback）

工作台“反馈与诊断”页的“快速诊断”按钮保留规则聚类路径（按问题类型计数归组），仅用于确定问题方向，不解读证据；作为智能诊断不可用时的兜底，产物同样进入提案审批流。

## 健康分析与运营报告

`kb_analyze` 工具（只读）提供四类健康分析：源冲突（同 source 多版本并存）、失败文档与抽取状态、重复实体候选（按规范化名称聚类）、检索缺口三分类（零命中查询重探分诊：知识缺失 / 检索波动 / 内容不全），报告落盘 reports/。`kb_report` 工具汇总近 N 天检索信号（查询总量、零命中率、高频查询）与健康指标。质量徽章实时反映 LightRAG 引擎健康状态。

已移除的能力：知识飞轮（kb_propose 提案门控、自证题、自动评测 golden 题库、回放层、内容指纹门控）与旧版改进建议账本——新版统一走“反馈 → 智能诊断 → 提案审批”流程。
