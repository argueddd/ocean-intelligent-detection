# 知识库功能说明（KnowledgeCore「知核」· 知识飞轮）

> **当前版本说明（2026-09-15）**：产品主流程已收敛为“反馈 → 诊断 → 提案审批 → 执行 → 复核”，详见 [重构后功能说明](重构后功能说明.md) 与 [REFACTOR.md](../REFACTOR.md)。本文保留历史设计细节，涉及自动评测、自动提交或复杂治理的内容不代表当前用户入口。


> 版本：v2.0 ｜ 日期：2026-09-14 ｜ 读者：具备一定编码与业务背景的运营/开发人员
> 配套文档：《知识库系统设计说明》（架构与机制）、《知识库操作手册》（日常操作流程）。

本文档描述 dsh-knowledge 插件（KnowledgeCore，知核）的**实际功能**，按"给谁用"组织：**会话内能力**（AI 与使用者）、**工作台可视化**（所有人）、**可靠性内核**（长稳运行）、**知识飞轮自动化**（越用越准）。

---

## 0. 系统定位与核心思想

知核是挂在 DeepSeek Harness 上的知识库引擎与知识底座，底层对接 LightRAG（图 + 向量双索引，rerank 关闭），向上提供三类能力：

| 层 | 说明 |
|---|---|
| 会话内能力 | 7 个模型工具，AI 在对话中自动检索、沉淀、更新、治理知识库 |
| 工作台可视化 | 浏览器内的运维控制台，人直接管理文档与图谱、看审计与体检 |
| 知识飞轮自动化 | 提案 → 评测门控 → 审批 → 生效的闭环，让知识库"越用越准" |

v2 的核心反转：**注册表（harness 侧元数据账本）是事实源，LightRAG 引擎是物化视图**。一个持续对账的收敛器让引擎不断逼近注册表意图；所有写操作必须经过单一写入口（chokepoint），绕过审批/门控在结构上不可能。

## 1. 总体架构（模块清单）

| 模块 | 职责 |
|---|---|
| `lib/engine-port.js` | LightRAG 适配层，唯一知道引擎怪癖的地方（异步删除、忙时 409、同 source 重插 409、内容寻址 doc_id、GraphML 不支持数组等） |
| `lib/registry.js` | 文档注册表 + 审计流水（内存索引 byId/bySource，防抖落盘） |
| `lib/intent.js` | 意图账本 + 串行执行器：文档类变更先落盘再执行，重启不丢 |
| `lib/reconciler.js` | 收敛器：启动 + 周期对账，让引擎 ≡ 注册表 |
| `lib/service.js` | 单一写入口，origin 策略链（user/agent/flywheel/system） |
| `lib/curator.js` | 检索日志 + 提案账本 + golden 分层（smoke + 回放层） |
| `lib/gate.js` | 门控：自证题 + 指纹锚定的 golden 回归；回滚失败绝不静默 |
| `lib/analyze.js` | 五类健康分析 + 运营周报（全只读） |
| `lib/store.js` | 存储原语：原子写、防抖 JSON、append-only JSONL + 压缩 |
| `lib/fake-engine.js` | 与真实引擎同接口的内存实现，契约测试用（模拟全部引擎怪癖） |

存储位置：`${DSH_HOME:-$HOME/.dsh}/storages/dsh-knowledge/`；引擎地址默认 `http://127.0.0.1:9623`（可用 `LIGHTRAG_BASE_URL` 覆盖）。

## 2. 会话内能力（7 个模型工具）

在 dsh 对话中，AI 按需调用下列工具；使用者也可用自然语言指挥（如"帮我查差旅报销标准""把这条结论沉淀进知识库""做一次知识库体检"）。

### 2.1 检索与状态

| 工具 | 功能 | 说明 |
|---|---|---|
| `lightrag_query` | 检索知识库并返回带引用答案 | 6 种模式：`mix`（图+向量混合，默认）/`local`/`global`/`hybrid`/`naive`/`bypass`；返回正文 + 引用文档列表 |
| `kb_status` | 引擎健康与统计 | 版本、处理队列、文档状态分布、意图账本积压、失败文档清单 |

检索纪律（由 `kb-usage` 技能约束）：涉及公司制度/流程/规范的问题必须先检索再作答并标注引用；检索无结果时明确说明，不得编造。

### 2.2 知识沉淀 `kb_ingest`

| 来源 | 说明 |
|---|---|
| `file` | 工作区文件路径（docx/md/txt/xlsx/pptx 等；PDF 因 MinerU 异常暂不建议）；强制工作区边界校验 + 100MB 上限，防任意主机文件入库 |
| `text` | 直接提供的文本 |
| `conversation` | 会话产出的结论，正文必须是结论化表达（不含闲聊） |

沉淀是异步的：先写入意图账本再执行，完成后用 `kb_status` 查进度。**同一来源重复沉淀会被拒绝**（409），更新请走 `kb_update` 替换。沉淀在审计 + 账本中可回退，故模型发起不额外要求审批。

### 2.3 知识更新 `kb_update`

| 类别 | 动作 | 说明 |
|---|---|---|
| 文档 | `replace` | 用新文件替换，走意图账本（先删旧核验消失、再插新），全程可恢复 |
| 文档 | `delete` | 退役文档（软删除，注册表保留审计） |
| 文档 | `retry` | 重试失败文档（幂等，显式 doc_id，免审批） |
| 图谱 | `entity_create` / `entity_edit` / `entity_merge` / `entity_delete` | 实体增删改与合并 |
| 图谱 | `relation_create` / `relation_edit` / `relation_delete` | 关系增删改 |

除 `retry` 外，模型发起的一切 `kb_update` 变更都**先请求人工审批一次**（`ctx.approval`），通过后才执行；所有操作写入审计。优先考虑用 `kb_propose` 走评测门控的自动生效路径。

### 2.4 治理与运营

| 工具 | 功能 | 说明 |
|---|---|---|
| `kb_propose` | 飞轮提案（推荐通道） | 带证据链与自证题的正式变更提案，走考试 + 审批（见 §5） |
| `kb_analyze` | 五类健康体检 | 全只读，产出结构化报告并落盘（见 §6.1） |
| `kb_report` | 运营周报/月报 | 近 N 天检索信号、提案飞轮、成绩趋势、健康概况（见 §6.2） |

## 4. 可靠性内核：单一写入口 + 意图账本 + 收敛器

### 4.1 单一写入口与 origin 策略

一切知识库变更（Web 路由 / 模型工具 / 门控 / 收敛器）都汇入 `service.js` 这一个 chokepoint，按 `origin` 决定放行：

| origin | 来源 | 放行规则 |
|---|---|---|
| `user` | Web 工作台（人已确认） | 直接执行 |
| `agent` | 模型工具 kb_update | 破坏性 + 图谱写必须 `approved`（审批通过），否则 403 |
| `flywheel` | 门控评测通过后应用 | 直接执行（门控即强制点） |
| `system` | 收敛器 / 意图账本 | 直接执行（账本即意图） |

豁免：`ingest`（沉淀，审计 + 账本可回退）与 `retry`（幂等修复，不改知识集合）。绕过门控不再是"纪律问题"，而是结构上不可能。

### 4.2 意图账本（变更先落盘再执行）

所有**文档类**变更（沉淀 / 删除 / 替换）先落盘为"意图"（`intents.jsonl`，WAL 式追加）再执行，重启后未完成的意图自动恢复续跑——不会再出现"说删了没删"的永久分歧。

- 状态机：`pending → issued → verifying → verified / failed / stuck`；`stuck` = 重试耗尽，可见、可手动重试，绝不静默。
- 串行执行器：同一时刻只跑一个意图（适配引擎单 worker）；删除前必须等管道空闲（忙时删除会被引擎静默丢弃）。
- **替换阶段机**：`delete_old`（先删旧并核验消失）→ `ingest_new`（插新）→ `track_new`（轮询至 processed）→ 注册表版本链提升（旧 doc 标 `outdated`，新 doc `active`，v+1）。崩溃从所处阶段继续。
- **崩溃窗口恢复**：上传已落地但状态行未写盘时重启，重插会 409「已存在」——此时按 source 找回已插入文档转核验，不误报失败。
- 文件字节不入 JSONL：先落 `spool/<intentId>.bin`，终态后清理；恢复时 spool 丢失 → 意图转 failed（要求重新提交）。

### 4.3 收敛器（持续对账）

启动与周期（默认 10 分钟）全量对账，让引擎持续逼近注册表意图：

| 情形 | 处理 |
|---|---|
| 引擎有、注册表无 | 收养（幂等，单条汇总审计 `registry_adopted`） |
| 注册表 active/processing、引擎无、且无进行中意图 | 标 `missing`（进入待办） |
| 注册表 retired、引擎仍在 | 补删意图（低优先级，对账补删） |

进行中意图覆盖的文档在对账时豁免，避免误判。

## 5. 知识飞轮（kb_propose）

提案是知识变更的**原子交易单位**：一条提案一个操作，全程留痕，让知识库"越用越准"。

### 5.1 提案必须携带

| 字段 | 要求 |
|---|---|
| `op` | 操作类型（见 §5.2） |
| `evidence` | 证据链（必填）：命中的 chunk/文档 + 会话/消息引用 |
| `rationale` | 理由（必填）：自然语言说明为什么成立 |
| `verify_query` + `verify_expect` | 自证题（additive 必填）：一道证明"这条知识有用"的考题及期望（docs 全文命中 + facts 全文命中 + entities 至少一个） |

自证题来源优先级：query_log 中失败的原查询 > 用户原始提问 > AI 自构。

### 5.2 操作分类与放行方式

| 类别 | op | 放行方式 |
|---|---|---|
| additive（增量） | `entity_edit` / `entity_create` / `relation_create` | 自动跑双条件评测门控，通过后默认自动提交生效（可配置改人工） |
| 文本入库 | `text_ingest` | 人工审批（异步抽取成本高，不自动评测） |
| 破坏性 | `delete_doc` / `entity_merge` / `entity_delete` / `relation_delete` | 人工审批（人工即门控） |

### 5.3 双条件评测门控（additive）

```
自证题·改前：现网答不上 → 才值得做（答得上 = 冗余，直接拒绝，不应用任何变更）
        ↓ 应用改动
自证题·改后：必须答得上（答不上 = 无效，自动回滚并拒绝）
        ↓
回归考试：golden 考题重跑，「找得到/读得全」两项不许掉（容差 2%，掉则自动回滚并拒绝）
        ↓
通过 → 生效并记账；未通过 → 拒绝并回滚（知识库毫发无损）
```

- 基线在**提案应用之前**测量，缓存键 = 内容指纹 + 题集指纹；库内容变或题集变即失效重跑，杜绝"缓存期间库漂移全算提案 delta"的失真。
- **回滚失败绝不静默**：落审计 + 提案标 `stuck` + 返回 `degraded`（人工介入）。entity_edit 前值捕获失败时自动降级人工审批（绝不"应用了却回不了"）。
- 判定只看文档命中率 + 引用覆盖率；实体命中率只记录趋势不入判定（实测单轮噪声 3%–7%）。

### 5.4 golden 分层与自证题晋升

| 层 | 来源 | 作用 |
|---|---|---|
| smoke | 包内 `golden/golden.yaml` 手写题（29 题，全部来自真实制度文档） | 冒烟回归 |
| replay_promoted | 已生效提案的自证题自动晋升（上限 100） | 门控强判定 |
| replay_sampled | 生产查询采样（上限 150） | 软期望，只记录趋势不入判定 |

生效提案的自证题自动晋升进回放题库——题库随使用生长，实现"越用越准"。

### 5.5 提案状态机

`待评估(proposed) → 评估通过(eval_passed) / 已拒绝(rejected) → 已批准(approved) → 已生效(committed)`

- text_ingest / delete_doc 提案提交后停在 `approved + intent_ref`，由图谱外意图账本终态回调升 `committed` / 降 `rejected`（引擎真正处理完才算生效）。
- 每次状态迁移追加审计行；生效时记录提交审计引用，与 `curation_runs/commit_log.jsonl` 互引。

## 6. 健康分析与周报

### 6.1 五类健康体检（kb_analyze，全只读）

| 体检项 | 数据来源 | 产出 |
|---|---|---|
| 源冲突 | 引擎 `/documents/source_conflicts` | 同 source 多版本并存清单 |
| 失败文档 | 注册表 + 引擎状态统计 | 失败清单与重试建议 |
| 重复实体候选 | 活库 GraphML 流式扫描，按规范化名称聚类（需 `KB_RAG_STORAGE`） | 同名变体清单（如 eNodeB/ENODEB），别名法合并素材 |
| 检索缺口 | query_log 零命中查询重探 `/query/data` 分诊 | 三分类 + 每项处置建议（见下） |

检索缺口三分类：

| 类别 | 含义 | 建议 |
|---|---|---|
| `a-missing` | 知识不存在 | 采购：联网调研后 text_ingest 验证入库 |
| `b-retrieval-jitter` | 同参数重试即命中 | 检索波动，观察趋势 |
| `b-missing-text` | 实体在、条文不在 | 描述增强（entity_edit）或补条文（text_ingest），最有价值 |

报告落盘 `reports/analysis-<日期>.md`（人读）+ `.json`（结构化）。

### 6.2 运营周报（kb_report）

近 N 天（默认 7）自动汇总：查询总量与零命中率、高频查询、提案数量与状态分布、批准率、已生效提案的门控 delta、golden 趋势、健康概况。落盘 `reports/weekly-<日期>.md/.json`。

## 7. 存储与账本

### 7.1 落盘文件（`storages/dsh-knowledge/`）

| 文件 | 形态 | 内容 |
|---|---|---|
| `registry.json` | 单 JSON（防抖原子写） | 文档注册表 + settings |
| `audit.jsonl` | append-only | 审计流水 |
| `intents/intents.jsonl` + `spool/` | WAL + 字节暂存 | 意图账本 |
| `query_log.jsonl` | append-only | 检索流水 |
| `proposals.jsonl` | append-only（同 id 末行生效，超阈值压缩） | 提案账本 |
| `replay.json` | 单 JSON | 回放层（晋升 + 采样） |
| `golden.yaml` / `reports/` | 版本化文件 | 考试卷与基线/分析/周报 |

### 7.2 三本账

| 账本 | 回答的问题 |
|---|---|
| 查询流水 query_log | "用户问过什么、查到没有" |
| 提案账本 proposals + 审计 audit | "谁、何时、凭什么改了知识库" |
| 成绩档案 baselines | "知识库变好了还是变坏了" |

### 7.3 指标口径（口语名 / 精确名）

| 口语名 | 精确名 | 含义 |
|---|---|---|
| 找得到 | 文档命中率 | 该找到的文档找到没有 |
| 认得全 | 实体命中率 | 关键概念认出来没有（仅趋势，不入门控） |
| 读得全 | 引用覆盖率 | 关键内容读到没有 |
| 没查到比例 | 零命中率 | 检索无结果占比（越低越好） |
| 批准率 | 提案批准率 | 已生效 /（已生效 + 已拒绝） |

## 8. 能力边界（如实说明）

- 破坏性操作不自动考试，靠人工审批把关；
- 文本入库不参与自动考试（人工审批路径）；
- 实体完整合并依赖引擎 `/graph/entities/merge`；重复实体候选需配置 `KB_RAG_STORAGE`（活库宿主路径）方能扫描；
- 用户反馈（踩赞）与历史会话的双源信号合并尚未接入，当前以 query_log 为主源；
- 多知识库（分部门分库）接口自始预留 `kb` 参数，MVP 仅启用默认库 `company`；
- PDF 沉淀因 MinerU 异常暂不建议（当前依赖引擎侧解析能力）。
