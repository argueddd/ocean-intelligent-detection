# KnowledgeCore 简化重构开发文档

## 目标

KnowledgeCore 为用户提供一条可理解、可追踪的修复路径：用户对回答进行反馈，智能体从反馈、对话、引用和知识库状态中诊断问题，生成少量修复提案，用户确认后由后台任务执行，系统再用原问题进行一次轻量复核。

第一版不承诺自动学习，也不启用自动改库。它提供反馈驱动的知识库诊断与修复。

## 产品范围

### 用户流程

1. 用户提问并获得带引用的回答。
2. 用户点击“有帮助”“没帮助”或选择具体问题类型。
3. 用户点击“诊断知识库”，选择时间范围或反馈记录。
4. 智能体将反馈按根因归并，并最多生成 3 张推荐提案卡。
5. 用户查看证据、修改建议、批准或拒绝提案。
6. Harness 意图任务执行文档或图谱变更。
7. 系统重新执行原问题，展示引用变化并请求“已解决/仍有问题”反馈。

### 问题分类

- 引用文档不对：替换、退役或调整文档来源。
- 引用内容不完整：补充文本或替换原文。
- 实体不准确：修改实体描述或建立规范名称。
- 关系不准确：修改、删除或新增关系。
- 内容缺失：生成待确认的新增资料提案。
- 内容过期：根据生效时间和权威来源替换旧文档。
- 回答表达问题：记录为模型回答问题，暂不修改知识库。

“chunk 不准确”只作为用户可见的反馈标签。系统将它归并为具体的文档或检索修复动作，不直接编辑 chunk。

### 数量规则

- 一次诊断最多读取 50 条反馈。
- 相同根因的反馈合并为一个问题簇。
- 默认显示最多 3 张高优先级提案卡。
- 后端最多保留 10 个候选问题，其余反馈等待下一次诊断。
- 单条反馈通常生成 0 或 1 张主提案。

优先级由影响范围、出现频率、诊断置信度和可修复性共同决定。高风险提案单独成卡，不与其他变更合并。

## 数据模型

### 查询记录

`query_log.jsonl` 中每条记录包含 `query_id`、问题、回答摘要、引用、会话消息、耗时和反馈状态。回答正文按部署的隐私策略保存；默认保留摘要和哈希，不保存不必要的敏感全文。

### 反馈记录

`feedback.jsonl` 追加保存 `feedback_id`、`query_id`、`session_id`、`message_id`、`rating`、`issue_type`、用户说明、时间和处理状态。

反馈表示“可能有问题”，不直接作为事实来源。智能体必须在提案中展示原问题、原回答、引用片段和可验证的资料依据。

### 提案状态

```text
candidate → awaiting_approval → approved → executing → succeeded
                                      └──────→ rejected
                                      └──────→ failed
```

提案卡包含问题、证据、判断、变更预览、影响、风险、执行计划和回滚计划。用户批准的是一组完整的执行步骤，后台可以将步骤拆成多个意图任务。

## 执行边界

- 所有模型生成的知识变更都需要用户批准。
- 会话总结不能直接发布为正式知识，只能生成待审核的新增资料提案。
- 文档和图谱变更继续通过 `service.js` 单一写入口。
- 文档类任务继续使用 `intent.js` 的持久化状态、重试和重启恢复。
- 执行成功后才发布成功事件和更新提案状态。
- 执行失败必须保留失败原因，并提供重试入口。

第一版不包含自动门控、golden 题库、自动提交白名单、复杂周报、全量实体扫描、多知识库和图谱可视化工作台。

## 轻量复核

正式评测暂时下线。每条成功提案只重新运行触发反馈的原问题，并展示：

- 执行前后的引用文档；
- 引用片段是否变化；
- 重新查询耗时；
- 用户是否确认问题已解决。

产品指标使用问题解决率、修复后重复负反馈率、提案批准率、执行成功率和平均修复时间。

## 模块调整

保留 `engine-port.js`、`service.js`、`intent.js`、`registry.js` 和基础审计。新增 `feedback.js` 与 `diagnosis.js`，并将提案执行状态收敛到统一的 proposal service。

现有 `curator.js`、`gate.js`、`analyze.js` 的旧评测和周期治理接口暂不作为默认用户入口。代码可以保留为迁移期兼容模块，但不得被新 UI 或新工具调用。

## 验收标准

1. 用户可以在一条回答上提交评分和问题类型。
2. 同一查询的重复反馈可去重，并能按反馈状态筛选。
3. 诊断一次最多展示 3 张推荐提案，提案包含证据和风险。
4. 模型不能绕过审批直接修改实体、关系或正式文档。
5. 用户批准后任务可在宿主重启后继续执行。
6. 成功和失败都能在提案记录中看到，并可重试失败任务。
7. 成功修复后可以重新查询原问题并提交“已解决/仍有问题”。
8. 所有新增接口和状态都有单元测试和一次真实 Loader 入口冒烟测试。

## 未决事项

- 回答正文的保留时长和脱敏规则由部署方确定。
- 文档有效期和权威等级字段需要结合实际制度来源补充。
- LightRAG 的 chunk 级引用字段需要以当前服务返回值为准，不能用文件名代替定位信息。
